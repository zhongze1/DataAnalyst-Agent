# DA-017: 配额与并发保护（PRD W2-3）

- **类型**: Feature
- **优先级**: P1
- **预估工时**: 6–8 小时
- **前置依赖**: DA-002（request_id 追踪）、DA-003（统一错误响应）、DA-008（审计）、W2-1.5（用户体系 / 会话归属）

## 描述

**用户故事**：作为部署方，系统开始被多人同时使用后，我需要限制单人/单会话的提问频率与并发，
避免单个用户把 LLM 费用或服务容量吃满；同时，被限制的用户必须看到**人话提示**，
而不是一个看不懂的报错或长时间转圈。

**现状证据**：全仓无任何限流/配额/并发控制（`grep 限流|配额|quota|rate_limit|Semaphore` 只命中注释）。
`/api/chat`（`app/routers/chat.py:17`）与 `/api/chat/stream`（`app/routers/chat_stream.py:36`）
两个入口均可被无限次并发调用，每次调用都会真实产生 LLM 费用。

**做什么**：
1. 请求次数硬配额：每用户每分钟 10 次、每用户每日 50 次、每会话每分钟 5 次。
2. 并发保护：每用户同时最多 1 个 Agent 请求；全局最大并发由配置控制，默认 4。
3. Token 用量统计：修复 Agent Loop usage 覆盖问题，逐轮累加并持久化可获得的用量（**第一版不作为硬拒绝条件**）。
4. 超限友好提示：HTTP 429 + 统一错误体，SSE 在推流前完成预检。

**不做什么**（明确边界）：
- 不做队列/排队，超限立即拒绝。
- 不做多 worker 的全局一致限流（第一版明确只支持单进程部署）。
- 不做额度仪表盘 / 剩余次数 UI（只复用现有错误提示机制，必要时禁用发送按钮）。
- 不改 Agent Loop 的循环结构，不引入新的第三方依赖。
- 不覆盖上传、导出、历史列表、重置接口的配额（配额目的是控 LLM 费用，这些接口不产生模型调用）。
- 不顺带修复本工单之外的问题（例如 `app/routers/chat.py:21` 缺 `UserRecord` 导入），另开工单。

## 验收标准（Given-When-Then）

### 一、请求次数配额

1. **Given** 认证开启、用户 U 已知，**When** U 在第 1 分钟内发出第 11 次提问，**Then** 返回 429，
   错误码 `QUOTA_EXCEEDED`，且第 11 次**没有**调用 LLM（用 Mock 断言调用次数）。
2. **Given** U 在第 1 分钟已用满 10 次，**When** 时间推进到第 2 分钟，**Then** U 可以再次提问成功
   （窗口滚动后额度恢复）。
3. **Given** 用户 U 当日已用满 50 次，**When** U 再次提问，**Then** 返回 429 `QUOTA_EXCEEDED`，
   文案中的重置时间与实际配额重置时刻**一致**（同一个时区对象算出）。
4. **Given** 用户 U 当日已用 50 次，**When** 进程重启（新 repository + 新 QuotaService 指向同一 db），
   **Then** U 的当日计数仍为 50，仍被拒绝（计数已持久化）。
5. **Given** 会话 S 在第 1 分钟内已被提问 5 次，**When** 同一会话第 6 次提问，**Then** 返回 429 `QUOTA_EXCEEDED`。
6. **Given** 会话 S1 用满，**When** 同一用户改问会话 S2，**Then** 用户分钟额度未满时请求正常
   （会话维度与用户维度**互相独立**，不混为一个计数）。
7. **Given** 认证关闭（本机模式），**When** 连续提问超过每分钟上限，**Then** 同样被限流，
   使用固定的本机用户键（不会因 `user is None` 而跳过限流）。

### 二、并发保护

8. **Given** 用户 U 已有 1 个请求在执行中（LLM 阻塞），**When** U 的第 2 个请求到达，**Then** 立即返回 429
   错误码 `TOO_MANY_CONCURRENT`（**不排队、不等待**），且第 2 个请求没有调用 LLM。
9. **Given** 两个请求**同时**到达（同一用户），**When** 两个协程并发进入预检，**Then**
   **有且仅有一个**通过（检查+占用必须是原子的，不允许两个都通过）。
10. **Given** 全局并发上限为 N 且已有 N 个请求在跑，**When** 第 N+1 个请求（不同用户）到达，
    **Then** 返回统一的友好错误响应（429 `SERVER_BUSY`），适用时带 `Retry-After` 响应头。
11. **Given** 一个请求已通过预检并占用并发，**When** 它正常结束 / 抛异常 / 被取消 / 客户端断开，
    **Then** 并发占用**一定被释放**（后续请求不再被误判为并发超限）。
12. **Given** 请求在预检阶段就被拒绝，**When** 后续请求到达，**Then** 计数与并发占用**没有**被写入
    （不允许"部分占用"或失败请求重复计数）。

### 三、接口与错误契约

13. **Given** `/api/chat/stream` 的请求已超限，**When** 调用该接口，**Then** 返回**标准 JSON 错误响应**
    （不是 SSE 帧、不是开始推流后中断），状态码 429，体形如 `{"error": {code, message, request_id}}`。
14. **Given** 任意超限响应，**When** 检查响应体，**Then** `message` 是人工文案，
    不含堆栈、类名、本地路径、API Key。
15. **Given** 超限响应，**When** 检查响应头，**Then** 存在 `Retry-After`（整数秒），
    且 `X-Request-ID` 仍然存在（沿用现有中间件契约）。
16. **Given** 前端现有错误处理（`app/web/static/app.js:63-79`、`305-313`），**When** 收到 429，
    **Then** 无需改动契约即可显示后端文案（复用现有通道）。

### 四、Token 用量统计

17. **Given** 一次提问触发了多轮模型调用，**When** 检查最终 `AgentResult.usage` / `ChatResponse.usage`，
    **Then** 输入/输出 token 是**各轮累加值**，不是最后一次的值。
18. **Given** 达到 `max_agent_steps` 后的收尾调用产生了 usage，**When** 检查最终 usage，
    **Then** 该轮用量**也被计入**。
19. **Given** 某一轮模型返回的 usage 缺失或为空，**When** 累加，**Then**
    不抛异常、不把估算值伪装成精确 usage；缺失轮次另有计数可查。
20. **Given** 流式请求，**When** 厂商在流结束时才返回 usage，**Then** 该 usage 被正确计入。

### 五、配置与兼容

21. **Given** 未新增任何环境变量（沿用现有 `.env`），**When** 启动服务，**Then**
    启动成功、配置校验通过、使用默认配额值（不因新增配置导致升级后无法启动）。
22. **Given** 配置了非法的配额值（如 0 或负数），**When** 启动，**Then**
    `validate_settings` 给出明确的 ConfigProblem（沿用现有 fail-fast 规范）。
23. **Given** 所有配额项可配置，**When** 通过环境变量调整上限，**Then** 行为随之改变（有测试覆盖）。
24. **Given** 本工单改动完成，**When** 运行 `uv run python -m pytest -q`，**Then**
    原有全部用例（423 个）与新用例**全绿**。

### 六、审计与安全

25. **Given** 发生一次配额拒绝，**When** 检查审计记录，**Then** 存在对应事件
    （含 request_id、维度、命中的限制），且**不含**密码、Cookie、原始提示词、完整业务数据。
26. **Given** 任意配额状态（SQLite 表 / 内存计数），**When** 检查内容，**Then**
    不含用户口令、令牌、提示词原文。

## 备注（关键设计决策与约束）

1. **原子性来自"不 await"**：`QuotaService` 的 `reserve()` / `release()` / `settle()` 都是**同步方法**。
   在 asyncio 单事件循环下，同步方法内部不会被切走，检查+占用天然原子；
   若做成 `async def` 并在中间 await（例如 await 一次 DB），就会出现两个请求同时通过检查的竞态。
   同时这也是**取消路径**的要求：在 `CancelledError` 传播中 `await` 会立即失败，
   导致结算丢失、并发占用泄漏。
2. **明确区分预检 / 占用 / 结算 / 释放**：先做完所有只读检查，全部通过后再一次性占用；
   失败即抛异常且不留部分占用。请求顺序：会话校验 → 配额预检+占用 → `agent.run` → 结算 → 释放。
3. **计数分层**：分钟窗口与当前并发放进程内存（短期、可容忍重启清零）；
   每日请求计数与 token 用量落 SQLite（需跨重启保留）。
4. **时区与重置**：新增 `AGENT_QUOTA_TIMEZONE`（默认 `Asia/Shanghai`）。解析失败**只告警并回退 UTC**，
   绝不让服务起不来；提示文案的重置时刻与限流判定使用同一个 tz 对象计算，保证"说的和做的一致"。
5. **全局并发超限的错误码**：决策只指定了 `QUOTA_EXCEEDED` 与 `TOO_MANY_CONCURRENT`，
   全局并发超限使用 `SERVER_BUSY`（429 + `Retry-After` 头）。
6. **不改错误体契约**：`Retry-After` 只放响应头，不加入 `{"error": {...}}` 体 ——
   `tests/test_errors.py:36-39` 断言了错误体的精确键集，扩展会破坏既有契约。
7. **单进程假设**：进程内计数不跨 worker 共享；本工单不声称支持多 worker 全局一致限流，
   在 `README`/配置注释中写明。

### 已知限制

1. **单进程**：分钟窗口与当前并发的计数在进程内，多 worker 部署下各自计算
   （每日计数落 SQLite 是共享的，但并发上限会按 worker 数量放大）。
2. **每日计数写失败时拒绝请求**（fail-closed）：准入控制不能静默失效；
   与之相对，**用量结算**失败只记日志（那是观测，不是准入）。
3. **无 usage 时的轮次统计**：整轮都没拿到 usage 时按「1 轮未回报」计，token 保持 0，
   不估算、不伪装成精确值。
4. **未在本工单修复的既有问题**（按「不越界」原则另开工单）：
   - `app/routers/chat.py:21` 使用了 `UserRecord` 但未 import（当前 FastAPI 版本容忍）；
   - `app/agent/loop.py` 收尾请求失败时把异常文本直接拼进了给用户的答案（DA-010 同类，收尾分支漏改）。
5. **前端零改动**：现有 `setBusy` 已禁用发送按钮，错误路径已展示后端文案，满足「友好提示」要求。
   （额度仪表盘 / 剩余次数显示**不在**本工单范围。）
