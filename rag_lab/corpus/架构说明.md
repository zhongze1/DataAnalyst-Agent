# DataAnalyst Agent · 架构说明

> 本文是 RAG 实验语料之一，描述**主工程**的真实请求链路与关键模块。
> 所有模块名、函数名、事件名、表名都来自仓库代码；无法确认的部分标注「待确认」。

## 1. 分层

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 前端 | `app/web/`（`index.html` + `static/*.js`，无构建） | 上传、提问、渲染流式过程与结论、导出、历史会话 |
| 路由层 | `app/routers/` | HTTP 契约、依赖注入、鉴权与归属校验、配额预检 |
| 编排层 | `app/agent/` | 系统提示词、Agent Loop、事件定义 |
| 模型层 | `app/llm/` | `LLMClient` 协议、OpenAI 兼容实现、离线 Mock |
| 工具层 | `app/tools/` | 工具注册表、9 个 pandas 工具、`find_value`、沙箱校验 |
| 服务层 | `app/services/` | 认证、报告导出、配额与并发 |
| 存储层 | `app/storage/` | SQLite DAO、会话仓库、结构化产物 |
| 横切 | `app/config.py`、`app/errors.py`、`app/logging_setup.py`、`app/middleware.py`、`app/context.py`、`app/audit.py`、`app/security/` | 配置校验、统一错误、日志与请求上下文、审计、脱敏 |

分层纪律（代码注释中明确写下的约定）：

- **SQL 只允许出现在 `app/storage/` 的 DAO 文件里**，业务代码只依赖 `repository.py` 中的 Protocol；
- 路由层只通过 `app/dependencies.py` 的 `get_agent()` / `get_store()` / `get_quota_service()` 拿对象；
- `app/errors.py` 刻意不依赖 FastAPI，只把 HTTP 状态码作为元数据挂在异常类上，
  这样存储层也能抛业务异常而不引入框架依赖。

## 2. 请求处理链路（以非流式 `POST /api/chat` 为例）

```
HTTP 请求
  │
  ├─ RequestContextMiddleware（纯 ASGI，非 BaseHTTPMiddleware）
  │     · 生成或透传 X-Request-ID → 写入 scope 与 ContextVar
  │     · session_id ContextVar 复位为 "-"，避免上个请求串味
  │
  ├─ FastAPI 依赖注入
  │     · require_user()      → 认证开启且未登录则 401；认证关闭返回 None（本机模式）
  │     · get_store()         → SessionStore 单例（lru_cache）
  │     · get_agent()         → DataAnalystAgent 单例（lru_cache）
  │     · get_quota_service() → QuotaService 单例（lru_cache，进程内状态必须共享）
  │
  ├─ 路由体（app/routers/chat.py）
  │     ① store.get(session_id)；带了 session_id 却查不到 → SessionNotFoundError（404）
  │     ② set_session_id(...)：本次请求的日志与审计自动带上 session_id
  │     ③ quota.reserve(user_key, session_id)：预检并一次性占用计数与并发，
  │        超限直接抛 429（QUOTA_EXCEEDED / TOO_MANY_CONCURRENT / SERVER_BUSY）
  │     ④ await agent.run(session, message)   ← 核心
  │     ⑤ finally: quota.release(...)          ← 异常/取消也必须释放
  │     ⑥ quota.settle(reservation, result.usage)：结算 token 用量（失败只记日志）
  │
  └─ 返回 ChatResponse{session_id, answer, steps[], stop_reason, usage}
        · stop_reason ∈ {final, max_steps, llm_error, no_file}
        · 任何异常由全局处理器转成 {"error": {code, message, request_id}}
```

**顺序是有意的**：会话校验 → 配额预检与占用 → 执行 → 结算 → 释放。
这样"无效请求"不会吃掉额度，而"被拒绝的请求"也不会留下部分占用。

## 3. Agent Loop（`app/agent/loop.py`）

流程图：

```
用户问题
  ↓
组装消息：system prompt + 会话历史 + 本次提问
  ↓
┌─→ 调模型（可选流式）
│     ↓
│   模型要调工具？──是──→ 逐个执行工具 → 结果作为 role=tool 消息回灌 → 再调模型
│     │
│     否
│     ↓
└─  最终答案返回
```

关键点：

1. **循环上限**：`AGENT_MAX_AGENT_STEPS`（默认 12）。达到上限后**不直接丢弃**，而是追加一条
   "请停止调用工具、基于已有数据给阶段性结论"的 user 消息，再做一次收尾调用。
2. **工具异常不中断循环**：工具失败时把错误文本回传给模型，让它自我纠正。
   面向用户的 `ToolStep.error` 是**人话**（内部错误码经 `humanize_tool_error` 映射），
   而模型拿到的是**原始错误**（含错误码与细节）—— 这条"双通路"由 `app/tools/base.py` 的
   `encode_tool_error` / `split_tool_error` / `humanize_tool_error` 实现。
3. **模型调用是异步的，工具执行是阻塞的**：pandas 计算通过 `asyncio.to_thread` 放到线程池，
   避免卡住事件循环。
4. **usage 逐轮累加**：每次模型调用返回的 `usage` 会被累加（含触顶后的收尾轮、以及失败前已发生的轮次）；
   厂商未回报 usage 时**不估算**，只记录"未回报的轮次"数。
5. **统一收尾出口 `_finish`**：所有 `return` 都经过它，负责
   ① 落盘本轮对话（`store.save_turn`）；② 打印耗时与用量日志；
   ③ **任务漂移告警**（工具调用 ≥ 8 次但答案里没有出现提问中的任何关键词 → 只打 WARNING，不阻断）；
   ④ **对外的答案做敏感字段打码**（放在漂移检测之后，避免打码干扰关键词比对）。
6. **不暴露系统提示词**：system prompt 只进本轮 `working` 消息，不进 `steps`，也不回传前端。

## 4. 工具注册与执行（`app/tools/`）

- **注册**：`ToolRegistry` + 装饰器 `@tool(name=..., description=..., parameters=..., uses_active_frame=...)`。
  重名会直接 `ValueError`。`openai_schemas()` 把所有工具转成 OpenAI function-calling 的 JSON Schema。
- **执行**：`registry.run(name, arguments, ctx) -> (ok: bool, text: str)`，**永不抛异常**：

  | 情况 | 返回 |
  | --- | --- |
  | 工具不存在 | `ok=False`，错误码 `UNKNOWN_TOOL` |
  | 抛 `ToolError`（业务失败，如工作表/列不存在） | `ok=False`，错误码取该异常自带的 `code` |
  | 抛其他未预期异常 | `ok=False`，错误码 `RUNTIME_ERROR` |
  | 成功 | `ok=True` + 文本结果 |

  每次调用都会落一条审计记录（`app/audit.py`），只记参数"形状"与长度/指纹，不记参数内容。
- **上下文 `ToolContext`**：持有 `session_id / file_path / sheets / frames(DataFrame 缓存) / active_sheet`。
  `active_sheet` 是"`df` 现在指向哪张表"，**只允许由显式意图改变**（`load_sheet` 或 `run_pandas(sheet=...)`），
  只读工具不得偷偷改写；每次工具输出首行都会带 `[当前 df = 表名]` 标记，避免模型误判表。
- **沙箱**：`run_pandas` 用 AST 白名单校验模型写的代码 —— 禁止 `import` / `from ... import`、
  禁止以下划线开头的属性访问、禁止文件 IO（`to_csv`/`to_excel`/`read_*`/`open` 等一律拦截），
  `pd` / `np` / `df` 由沙箱预置。违反即返回 `SANDBOX_VIOLATION`。
- **产物**：`run_pandas` 的返回值若是 DataFrame/Series，会在返回前另存为 CSV
  （`app/storage/artifacts.py`），并写 `manifest.json`；超过 2000 行 / 50 列则不落盘但记一条说明。

## 5. 会话存储（`app/storage/`）

设计原则：**内存只是缓存，SQLite 才是真相**。

| 对象 | 位置 | 说明 |
| --- | --- | --- |
| 会话元数据 | `data/agent.db` 的 `sessions` 表 | session_id / 文件名 / 文件路径 / 工作表 / 时间 / 轮次 / owner_id |
| 对话消息 | 同库 `messages` 表 | `payload` 存**完整消息 JSON**（assistant 的 tool_calls、tool 的 tool_call_id 都在里面），保证重放无损；`steps_json` 挂该轮工具轨迹快照 |
| 每日用量 | 同库 `quota_daily_usage` 表 | 请求数 + token 用量 + "是否回报 usage"的轮次统计 |
| 上传文件 | `data/uploads/<session_id>/<原文件名>` | pandas 需要真实文件路径，因此文件留在磁盘 |
| 结构化产物 | `data/uploads/<session_id>/artifacts/*.csv` + `manifest.json` | 导出报告的数据来源；落盘前过脱敏 |
| 审计日志 | `data/audit/YYYY-MM-DD.jsonl` | 与运行日志分开：日志给运维、审计给合规 |

- 读路径：内存缓存 → repository → 重建 `Session`；
- 写路径：`save_turn` 把本轮消息**整体替换**写库（消息只有几十条，增量追踪容易因中途异常而顺序漂移）；
- SQLite 用 WAL + `busy_timeout`，连接 `check_same_thread=False` 并配一把进程内锁 ——
  **单进程假设**，项目明确不跑多 worker。

## 6. 流式响应（SSE）

- **契约**：帧格式为 `event: <kind>\ndata: <json>\n\n`，事件定义集中在 `app/agent/events.py`：

  | 事件 | 时机 | 载荷要点 |
  | --- | --- | --- |
  | `start` | 开始分析 | 问题长度、可用工具数 |
  | `tool_args` | 即将执行某工具 | step、tool、参数摘要（让 UI 立刻显示"正在执行 X"） |
  | `step` | 某工具执行完毕 | step、tool、ok、耗时、结果字符数、错误码 |
  | `token` | 答案增量文本 | text |
  | `done` | 全部结束 | 完整快照：answer + steps[] + stop_reason + usage |
  | `error` | 流中途失败 | code + message |

- **实现要点**（`app/routers/chat_stream.py`）：
  1. 与一次性接口**共用** `agent.run()`，区别只是传了 `on_event` 回调；
  2. Agent 把事件塞进 `asyncio.Queue`，由一个独立 task 跑分析，主协程消费队列并转成 SSE；
  3. **配额预检发生在建立流之前** —— 一旦开始推流就再也改不了状态码，
     所以超限必须在此之前抛出，由全局处理器返回标准 JSON 429；
  4. 客户端断开（"停止生成"/关页面）→ 生成器被取消 → `finally` 里 `task.cancel()`；
     被取消任务的 `finally` 会**同步**释放并发占用并结算用量（同步调用不受取消影响，
     用 `await` 则会在 `CancelledError` 传播时立刻失败，导致并发泄漏）；
  5. 响应头带 `Cache-Control: no-cache` 与 `X-Accel-Buffering: no`，避免反向代理把流缓冲成一坨。

## 7. 横切关注点

| 关注点 | 做法 |
| --- | --- |
| 配置 | `app/config.py` 的 `Settings`（前缀 `AGENT_`，可读 `.env`），启动时 `validate_settings` fail-fast，问题带修复建议 |
| 错误 | 所有可预期错误继承 `AppError`（自带 `code` 与 `http_status`）；`message` **只能是人写的文案**，真实异常放 `cause` 只进日志 |
| 日志 | text / json 两种格式；`request_id` 与 `session_id` 走 ContextVar，**只用于观测，不参与业务判断**；约定 `extra` 键不得撞 LogRecord 内置属性 |
| 认证 | 口令 PBKDF2 + 服务端登录会话（Cookie 里是令牌，库里存 SHA-256 指纹）；用户不存在与口令错误共用同一文案与同一耗时，堵用户枚举 |
| 归属隔离 | 非本人会话一律按"不存在"返回 **404 而非 403**（403 等于承认该 id 存在） |
| 脱敏 | `app/security/redact.py`：手机号/身份证/银行卡/邮箱规则 + 列名关键词；只对外（界面、导出、产物）打码，喂给模型的仍是原文 |
| 配额 | `app/services/quota_service.py`：分钟窗口与并发放进程内，每日计数落 SQLite；`reserve/release/settle` 全是**同步方法**以保证原子性与取消安全 |

## 8. 关键设计取舍

1. **超限即拒、不排队**：单次分析动辄几十秒，排队会把用户挂死且费用不可控。
2. **准入控制 fail-closed，观测 fail-open**：每日计数写失败 → 拒绝请求；
   用量结算写失败 → 只记日志（统计不能连带用户请求失败）。
3. **给模型的通路与给用户的通路必须分开**：错误信息、脱敏、打码三处都遵守这条边界，
   否则"用户看不到内部细节"或"模型算错"必然违反其一。
4. **SQLite 而非 PostgreSQL**：单机单进程够用，换库只需新增一个 repository 实现；
   建表语句刻意保持在两库共同子集内。
5. **Mock LLM**：离线、确定性的假模型让整条链路（含流式、工具调用、步数上限）都能在测试里跑通。
