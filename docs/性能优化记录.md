## 1. 已做的优化（有量化）

| # | 优化项 | 做法 | 量化结果 | 证据 |
| --- | --- | --- | --- | --- |
| 1 | 知识库工件**每进程只解析一次** | `get_knowledge_service()` 用 `lru_cache(maxsize=1)` 做进程级单例 | 工件 1.67 MB / 73 片段，一次加载 **32.3 ms**；之后所有请求复用同一实例（0 ms） | `app/services/knowledge_service.py` |
| 2 | BM25 索引**懒构建** | `_bm25_index` 首次检索时才建 postings，之后常驻 | 首次检索 **12.31 ms**（含索引构建）；预热后中位 **0.035 ms**、p95 **0.041 ms** | 同上；测量命令见文末 |
| 3 | 查询向量**不重复计费** | 进程内 LRU 缓存 `sha256(query)[:16]`，上限 256 条，不落盘 | 相同查询不重复调用向量服务（纯标点查询**一次都不调**，有专门用例守着） | `app/services/knowledge_service.py`、`tests/test_knowledge_service.py::test_pure_punctuation_query_skips_embedding` |
| 4 | 混合检索的**融合池加深** | 在每路前 `4×k` 上做 RRF 再截到 k（而非只在 top-k 上融合） | hybrid recall@5 **0.944 → 1.000**（18/18），MRR 0.858；vector/keyword 单路各漏 1 题，混合补齐 | `rag_lab/eval/report.md` |
| 5 | 工具输出预算 **1200 → 2400** | 预算做成**硬上限**（正文配额按剩余预算 ÷ 剩余命中数分摊），既不给模型灌长文、也不让第一条顶穿预算 | 同一提问的 `knowledge_search` 调用次数 **12 次 → 3 次**（模型不再为了"凑齐被截断的片段"反复改写查询）；单次输出 2339 / 2031 / 2236 字，均 ≤ 2400 | `app/config.py`（`knowledge_max_chars` 注释）、`app/tools/knowledge_tools.py` |
| 6 | 向量化**追加写 + 立即落盘** | 每批算完立刻写缓存文件，缓存键含「空间(provider/model/dim) + 内容指纹」 | 命中缓存时**一次服务都不调**（73 命中 / 0 计算）；中途失败或 Ctrl-C 不白花钱，重跑自动续上 | `rag_lab/src/rag_lab/embedding.py`、`rag_lab/README.md` 实测块 |
| 7 | 干净环境**依赖可复现** | 锁定 `uv.lock`；从零 `uv sync` 可还原同一套版本 | 在干净目录 `uv sync` 退出码 0、生成 `.venv`，随后服务启动 `/api/health` 200（见交付验证报告第 4 项） | `uv.lock`、`pyproject.toml` |
| 8 | 检索**零新依赖** | 主工程内重写约 150 行检索（纯 Python + `math`；查询向量化复用已有 `httpx`） | 主工程依赖图未新增任何包（分块/向量库/分词库都没引入） | `app/services/knowledge_service.py`、`pyproject.toml` |
| 9 | 混合模式**单次检索耗时**（含网络） | 查询向量 HTTP 往返 + 本地两路检索 + RRF | 真实端点实测单次 `knowledge_search` **348 ~ 487 ms**（其中本地部分 < 1 ms，其余全是向量服务往返） | 端到端实测日志（见交付验证报告第 2 项） |

## 2. 已做的优化（定性，无基准数字）

| # | 优化项 | 做法 | 为什么值得 |
| --- | --- | --- | --- |
| 10 | pandas 不阻塞事件循环 | `asyncio.to_thread` 执行工具（CPU 密集） | 长分析不会卡住其它请求与 SSE 推送 |
| 11 | 进程级单例 | `get_settings` / `get_quota_service` / `get_knowledge_service` 用 `lru_cache` | 配置解析、配额状态、知识库工件都不必每请求重建；配额单例更是**正确性**要求（否则限流失效） |
| 12 | 工具输出截断 | `AGENT_MAX_TOOL_OUTPUT_CHARS`（默认 4000）+ 知识库自身的 2400 预算 | 防止把整表/整篇文档灌进上下文，控制 token 成本 |
| 13 | 会话 Excel 只读一次 | `ToolContext.frames` 会话内缓存 DataFrame | 同一会话多次提问不重复读盘解析 |
| 14 | 审计写入**可靠性优先** | 单次 open → write → close，加线程锁 | 工具调用频率低（一次分析十几次），用简单实现换取"不会漏记" |
| 15 | 配置**启动即校验** | `lifespan` 里 `validate_settings` fail-fast | 坏配置在启动时暴露，而不是等到用户提问才 500 |

## 3. 观察项：已知的代价与**没做**的优化

这些不是 bug，是当前量级下的有意取舍，如实列出：

| 项 | 现状 | 何时需要处理 |
| --- | --- | --- |
| **上下文随步数线性增长** | 实测一次普通提问 `total ≈ 30k tokens`（其中 prompt ≈ 27.9k）：每轮都把历史 + 工具结果重新发给模型 | 当单次提问经常超过 6~8 步、或 token 成本成为主要开销时，需要做历史裁剪 / 工具结果摘要 |
| **无向量数据库** | 73 片段全量暴力余弦（本地部分 < 1 ms） | 片段数到 10⁴~10⁵ 量级时 |
| **无 rerank** | RRF 只做排序融合，不产生新召回 | 召回率达标即可，暂不需要 |
| **无基准测试基线** | 没有 `pytest-benchmark` 之类的固化基准；本文数字是单次测量 | 需要做性能回归时再引入 |
| **单进程** | 配额分钟窗口与并发占用是进程内状态 | 要横向扩展 worker 时必须换共享存储（见 `DA-017`） |
| **BM25 对"续片"偏弱** | 表格续行/引用段与提问的 2-gram 重合天然偏低 | 需要更细的分块策略或真分词时（见 `rag_lab/README.md` 已知限制） |

## 4. 复现方式

```bash
# ① 知识库工件加载 + 本地检索耗时
uv run python -c "import time,os;from app.config import Settings;from app.services.knowledge_service import KnowledgeService;p=os.path.join(os.getcwd(),'data','knowledge','knowledge_index.jsonl');s=Settings(_env_file=None,llm_provider='mock',knowledge_index_path=p);t0=time.perf_counter();svc=KnowledgeService(s);print('load_ms=%.1f'%((time.perf_counter()-t0)*1000));t0=time.perf_counter();svc.search('敏感字段是怎么打码的');print('first_ms=%.2f'%((time.perf_counter()-t0)*1000));ts=[]
for _ in range(20):
    t0=time.perf_counter();svc.search('敏感字段是怎么打码的');ts.append((time.perf_counter()-t0)*1000)
ts.sort();print('warm_median_ms=%.3f'%ts[10])"

# ② 检索质量（recall@5 / MRR）——在 rag_lab 子工程里
cd rag_lab && uv run python -m rag_lab.evaluate && cd ..

# ③ 数据集真值 35 项断言
uv run python data/samples/verify_datasets.py

# ④ 全量测试与覆盖率
uv run pytest -q
```

```

warm_median_ms=0.035
```
