# DataAnalyst Agent・模拟公司任务流规则

> 版本：v1.0
> 适用项目：DataAnalyst Agent（FastAPI + Agent Loop + Pandas 工具）
> 核心玩法：你只拿到一张工单，扮演开发，带 AI 完成。PM / 测试 / Code Review 由规则驱动（AI 扮演或你切换视角）。



***

## 0. 设计原则



1. **信息隔离**：每次只发一张工单，你只知道工单里写的东西，模拟真实公司 "开发不需要知道全部背景"。

2. **流程不可跳**：待办 → 进行中 → 待 CR → 待测试 → 已完成，每一步有明确的准入准出。

3. **验收可追溯**：每张工单有验收标准，完成后逐条核对，不接受 "大概做好了"。

4. **Bug 与变更常态化**：测试会提 Bug，PM 会提变更，你需要处理中断，模拟真实节奏。

5. **代码即交付**：不写文档糊弄，必须改代码、跑测试、通过 CR。



***

## 1. 角色定义



| 角色                    | 谁来演         | 职责                     |
| --------------------- | ----------- | ---------------------- |
| **产品经理（PM）**          | AI 扮演 / 你切换 | 写需求工单、定验收标准、提需求变更、最终验收 |
| **开发（Dev）**           | **你（带 AI）** | 接单、实现、自测、提交 CR、修 Bug   |
| **测试（QA）**            | AI 扮演 / 你切换 | 写用例、执行测试、提 Bug、回归验证    |
| **Code Reviewer（CR）** | AI 扮演 / 你切换 | 审查代码质量、架构、安全、可维护性      |

> **单人模式玩法**
>
> ：你主要扮演 Dev。PM 发工单时你只看工单内容；CR 和 QA 环节由你切换视角，严格按规则审查自己的代码 —— 这是训练 "跳出自己看自己" 的能力。

## 2. 工单类型



| 类型         | 标识         | 说明                     |
| ---------- | ---------- | ---------------------- |
| **新功能**    | `Feature`  | 新增功能或能力                |
| **Bug 修复** | `Bug`      | 现有功能的缺陷                |
| **需求变更**   | `Change`   | 已交付或进行中需求的修改           |
| **技术债**    | `TechDebt` | 重构、优化、补测试等无直接用户可见变化的工作 |



***

## 3. 工单模板（每张工单必须包含）



```
# DA-XXX: [工单标题]

- **类型**: Feature / Bug / Change / TechDebt
- **优先级**: P0 / P1 / P2 / P3
- **预估工时**: X 小时
- **前置依赖**: DA-YYY（无则写"无"）

## 描述
[用户故事 / 问题现象。Bug 必须写复现步骤]

## 验收标准（Given-When-Then）
1. **Given** [前置条件] **When** [操作] **Then** [预期结果]
2. ...

## 关联代码/文件
- `app/xxx.py:行号`
- `tests/test_xxx.py`

## 备注
[约束、提示、注意事项]
```

### 优先级定义



| 级别     | 含义                    | 响应要求        |
| ------ | --------------------- | ----------- |
| **P0** | 阻塞性，系统不可用或数据错误        | 立即处理，中断当前工单 |
| **P1** | 严重，核心功能不可用或结果错误       | 24 小时内开始    |
| **P2** | 一般，功能有缺陷但有 workaround | 正常排期        |
| **P3** | 轻微，体验优化或边缘情况          | 有空再做        |

## 4. 状态流转



```
┌──────────┐    接单     ┌──────────┐   提交CR   ┌──────────┐
│  待办     │ ──────────→ │ 进行中    │ ─────────→ │  待CR     │
│ Backlog  │             │InProgress│            │CR Review │
└──────────┘             └────┬─────┘            └────┬─────┘
     ↑                         │ 拒绝/放弃                │ CR通过
     │                         ↓                         ↓
     │                    ┌──────────┐            ┌──────────┐
     │                    │  已拒绝    │            │  待测试    │
     │                    │ Rejected │            │   QA     │
     │                    └──────────┘            └────┬─────┘
     │                                                   │ 测试通过
     │                                                   ↓
     │                                              ┌──────────┐
     │                                              │  已完成    │
     │                                              │   Done   │
     │                                              └──────────┘
     │
     │  CR打回: 待CR → 进行中（标注"CR修改"）
     │  QA打回: 待测试 → 进行中（生成Bug子工单或标注"QA修改"）
     └─────────────────────────────────────────────────────────
```

### 状态准入准出规则



| 状态       | 准入条件           | 准出条件（进入下一状态）                                     |
| -------- | -------------- | ------------------------------------------------ |
| **待办**   | PM 创建工单，验收标准完整 | 开发接单，确认理解需求                                      |
| **进行中**  | 开发接单           | 代码完成 + 自测通过 + 测试用例通过 → 提交 CR                     |
| **待 CR** | 开发提交 CR        | CR 通过（无阻塞性问题）→ 进入待测试；CR 不通过 → 打回进行中              |
| **待测试**  | CR 通过          | QA 逐条验证验收标准 + 回归测试通过 → 已完成；发现 Bug → 打回或生成 Bug 工单 |
| **已完成**  | QA 验收通过        | 终态                                               |

## 5. 各角色详细规则

### 5.1 产品经理（PM）规则



1. **需求必须有验收标准**：不能只写 "做个 XX 功能"，必须用 Given-When-Then 写清可验证的标准。

2. **需求范围明确**：写清 "做什么" 和 "不做什么"，避免开发自行扩大范围。

3. **需求变更必须说明影响**：变更工单必须写清变更原因、影响的已有功能、是否需要重新评估工时。

4. **验收必须逐条核对**：PM 最终验收时，必须逐条核对验收标准，不接受 "基本满足"。

5. **不干预实现细节**：PM 只定 "做什么" 和 "验收标准"，不规定 "怎么做"。

### 5.2 开发（Dev）规则



1. **先理解再动手**：接单后先用自己的话复述需求和验收标准，确认无歧义再开始。

2. **不越界修改**：只做工单范围内的修改，不顺手改别的代码（发现别的问题单独提工单）。

3. **必须有测试**：

* Feature：新增对应测试用例

* Bug：先写一个能复现 Bug 的失败测试，再修复

* 测试必须覆盖正常路径 + 至少一个边界 / 异常情况

1. **提交前自测清单**：

* [ ] `pytest -q` 全绿

* [ ] 新增 / 修改的测试通过

* [ ] 代码符合项目现有风格（看同目录其他文件）

* [ ] 没有硬编码的密钥、路径

* [ ] 没有 `print` 调试语句（用 `logging`）

1. **CR 提交说明**：提交 CR 时必须写清 "改了什么、为什么这么改、测试怎么覆盖的"。

2. **CR 反馈处理**：

* 阻塞性问题：必须修改

* 建议性问题：可以讨论，但必须回应（同意修改或说明理由）

* 不允许无视 CR 反馈直接合并

### 5.3 Code Reviewer（CR）规则



1. **审查维度**（逐项检查）：



| 维度       | 检查点                             |
| -------- | ------------------------------- |
| **正确性**  | 逻辑是否正确？边界情况处理了吗？有没有 off-by-one？ |
| **可读性**  | 变量名清晰吗？函数职责单一吗？复杂逻辑有注释吗？        |
| **可维护性** | 有没有重复代码？耦合度高吗？容易扩展吗？            |
| **安全性**  | 有没有注入风险？有没有暴露敏感信息？沙箱校验够吗？       |
| **性能**   | 有没有明显的 O (n²) 可以优化？大数据量会崩吗？     |
| **测试**   | 测试覆盖了核心逻辑吗？有断言吗？测试了失败路径吗？       |



1. **反馈格式**：

* 阻塞性（必须改）：`[BLOCK] 文件:行号 - 问题描述 - 修改建议`

* 建议性（可讨论）：`[SUGGEST] 文件:行号 - 问题描述 - 修改建议`

* 表扬：`[GOOD] 文件:行号 - 做得好的地方`

1. **不做的事**：

* 不只说 "这里不好"，必须给具体修改建议

* 不纠结风格偏好（如空格 vs 制表符），以项目现有风格为准

* 不扩大审查范围，只审本次工单改动的代码

### 5.4 测试（QA）规则



1. **测试用例必须基于验收标准**：每条验收标准至少对应一个测试用例。

2. **测试用例覆盖**：

* 正常路径

* 边界情况（空值、最大值、最小值）

* 异常路径（工具失败、LLM 失败、文件损坏）

* 回归测试（关联的已有功能）

1. **Bug 工单必须包含**：

* 复现步骤（Step by step）

* 预期结果

* 实际结果

* 环境信息（Python 版本、操作系统、数据文件）

* 优先级判断

1. **回归测试**：Bug 修复后，必须验证：

* Bug 本身不再复现

* 相关功能没有被破坏

1. **测试通过标准**：所有验收标准逐条验证通过 + 无 P0/P1 Bug + 回归测试通过。

## 6. Bug 处理规则

### 6.1 Bug 生命周期



```
QA发现Bug → 创建Bug工单 → 开发接单 → 复现Bug → 写失败测试 → 修复 → 自测 → CR → QA回归 → 关闭
```

### 6.2 Bug 工单模板



```
# DA-XXX: [Bug标题]

- **类型**: Bug
- **优先级**: P0 / P1 / P2 / P3
- **发现版本**: [commit hash 或版本号]

## 复现步骤
1. ...
2. ...
3. ...

## 预期结果
...

## 实际结果
...

## 环境
- Python: 3.x
- OS: Windows / macOS / Linux
- 数据文件: [如果涉及]

## 关联工单
DA-YYY（如果是某个功能引入的）
```

### 6.3 Bug 修复规则



1. **先复现再修复**：必须先在本地复现 Bug，不能凭猜测改代码。

2. **先写失败测试**：写一个能复现 Bug 的测试，确认它失败，再修复。

3. **根因分析**：修复时必须写清根因（为什么会发生），不能只治症状。

4. **防回归**：修复后，失败测试必须通过，且全量测试不红。

## 7. 需求变更规则

### 7.1 变更触发场景



* PM 发现需求描述不清，需要补充

* 业务方改变主意

* 开发实现中发现技术限制，需要调整方案

* 测试发现验收标准有矛盾

### 7.2 变更工单模板



```
# DA-XXX: [变更标题]

- **类型**: Change
- **优先级**: P0 / P1 / P2
- **关联工单**: DA-YYY（被变更的原工单）

## 变更原因
...

## 变更内容
- 原需求: ...
- 变更后: ...

## 影响范围
- 影响的功能: ...
- 影响的代码: ...
- 是否需要重新评估工时: 是 / 否（原 X 小时 → 新 Y 小时）

## 验收标准变更
- 原标准第 N 条: ... → 变更为: ...
- 新增标准: ...
```

### 7.3 变更处理规则



1. **进行中的工单发生变更**：开发必须暂停，重新评估：

* 已完成的部分是否需要推翻

* 剩余工时是否变化

* 是否需要拆分成新工单

1. **已完成的工单发生变更**：创建新的 Feature 或 Change 工单，不修改原工单。

2. **变更必须经过 PM 确认**：开发不能自行决定变更需求，必须由 PM 发变更工单。

## 9. 怎么开始第一张工单

### 步骤 1：选单

从工单池挑一张（推荐从 DA-001 或 DA-009 开始，难度低、见效快）。

### 步骤 2：复述需求

用你自己的话写下：



* 这个工单要解决什么问题？

* 验收标准是什么？

* 涉及哪些文件？

### 步骤 3：实现



* 先看现有代码，理解上下文

* 写测试（Bug 类先写失败测试）

* 实现代码

* 跑 `pytest -q` 确认全绿

### 步骤 4：自测清单

按 5.2 节的提交前自测清单逐项检查。

### 步骤 5：CR（切换视角）

扮演 CR，按 5.3 节的审查维度逐项审查自己的代码，写出 `[BLOCK]` / `[SUGGEST]` / `[GOOD]` 反馈。有 BLOCK 就回去改。

### 步骤 6：QA（切换视角）

扮演 QA，按验收标准逐条验证，写测试用例执行记录。发现 Bug 就创建 Bug 工单回去修。

### 步骤 7：完成

所有验收标准通过，全量测试绿，标记工单为 "已完成"。

## 10. 评分与成长追踪（可选）

每张工单完成后，可以给自己打分：



| 维度       | 满分 | 评分标准                       |
| -------- | -- | -------------------------- |
| **需求理解** | 20 | 是否准确理解需求？有没有做多余的事？         |
| **代码质量** | 25 | CR 有没有 BLOCK？代码可读性、可维护性如何？ |
| **测试覆盖** | 25 | 测试是否覆盖核心逻辑和边界？有没有失败路径测试？   |
| **交付时效** | 15 | 是否在预估工时内完成？                |
| **流程规范** | 15 | 是否遵守了状态流转？CR/QA 反馈是否处理到位？  |

**总分 ≥ 90**：优秀，模拟资深开发水平

**80-89**：良好，中级开发水平

**70-79**：及格，初级开发水平

**< 70**：需要复盘，找出薄弱环节
